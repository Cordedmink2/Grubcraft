# The War Table, episode 3: Lessons learned
MIA: Welcome to the last episode of this first series of The War Table. I'm Mia.
SAM: I'm Sam. Episode one was the design, episode two was what's been built. This one is the lessons: what went wrong, what surprised the team, and what changed how the work gets done. Some of these are about game development, and some are about running a project with a team of AI sessions.
MIA: Let's start with a technical one that has a really clear story. The map that wasn't the same map.
SAM: Right. Remember from episode one, multiplayer only works if every computer runs exactly the same simulation. The battle rules were written with whole numbers from the start for exactly that reason. But the map generator, the code that builds the hills and rivers, used ordinary fractional maths, including the sine function to make rolling hills.
MIA: And that's a problem because?
SAM: Because sine is computed slightly differently on different chips and operating systems. The difference is tiny, in the last decimal places, but a hill a hair higher on the Mac than on the Windows PC means a soldier walks a slightly different path, and the two games slowly turn into two different battles. The multiplayer thread flagged that risk in its plan. The first guard was a fingerprint of the map: before a battle, every machine checks it has the same hills and water, and refuses to start if not.
MIA: But a guard isn't a fix.
SAM: Exactly. The real fix was rewriting the map maths with whole numbers too, with a custom sine and square root. Then a test pins the map fingerprints, so if anyone accidentally changes map making, the test fails. And later the rule was made mechanical: the simulation code isn't allowed to use fractional maths at all, and the automatic checks reject it.
MIA: So the lesson is?
SAM: A rule like "everything must be identical on every machine" has to be enforced by a machine. People and AIs both forget. If a rule matters, write a check that fails.
MIA: Which is basically the story of golden replays too.
SAM: It is. Five days of rapid changes to combat, pushing, charges, pathfinding and AI, by several threads at once. The question is: how do you know one thread didn't quietly change how battles play out? The golden replays answer that. Recorded battles that must replay identically. The review we'll get to in a moment found a gap next to them, though. Replay files didn't record which version of the battle rules made them, so after a rules change, an old replay would silently play out a different battle. Now every change that alters battles must re-record the golden replays and bump a simulation version number. Replays record that number, the replay viewer can say where an old replay starts to differ, and the lobby uses it to keep players on different rules apart.
MIA: The whole-codebase review found something similar, didn't it?
SAM: Several things, and the way the review was run is itself a lesson. Ten reviewers each looked at one area, and then independent sceptics checked every finding against the actual code. Some findings were thrown out. One reviewer claimed battle outcomes could differ between players, and the sceptics showed that was false. What survived was twenty-three verified items.
MIA: What was the most important one?
SAM: Probably this. In a network game, any player could send sandbox commands, the developer tools for removing regiments or changing unit stats. The host passed every command along without checking what kind it was. So a modified copy of the game could change everyone's armies mid-battle. Nobody had noticed because everyone plays honestly. The fix was simple once it was seen: the host now ignores those commands from other players.
MIA: And another was about who won.
SAM: Yes. Who won the battle was being decided outside the simulation, once per drawn frame, and by two slightly different rules in different places. The sceptics checked whether that meant players could disagree about who won, and they couldn't. But the timing depended on frame rate, and two rules for one question is asking for trouble. Now the simulation itself decides, the same on every machine and in replays.
MIA: There was a theme in that review about events, too.
SAM: Right. The simulation only published the state of the battle: where everyone is and how many are alive. So the sound and animation code had to compare one moment to the next and guess what happened. Did that regiment lose five men because of arrows, or melee? Which archers just fired? At fast-forward, the guesses went wrong and alerts got missed. Now the simulation reports what happened each step: arrows loosed and landing, losses, morale changes, clashes and ambushes. Sounds and alerts read that, and the right archers draw.
MIA: Let's go to balance, because there's a lot of hard-won knowledge there.
SAM: There is. Balance is measured by running hundreds of AI versus AI battles for each pairing of factions, on two separate sets of random seeds. The first lesson was about noise. One run of ninety battles can swing by five percent either way just from luck. So a change that looks like a two-point improvement might be nothing. The rule became: always check on two different sets of seeds, and never chase a single pairing.
MIA: And some stats turned out to be really sensitive.
SAM: Very. The Concord's Bone Pikes going from defence fifty-one to fifty-three swung the Concord's matchups by about fifteen points. The Brood Skitterlings' morale going from sixty-two to sixty-five swung one pairing by twelve to twenty points. And the spacing between Choir Shardlings, a tiny change from point six to point five, made the Choir far stronger. The team calls these steep knobs.
MIA: What was the biggest surprise?
SAM: That balance depends on the map. With woods on the map, every pairing sits close to fifty-fifty, except Brood against Choir. On bare maps with no cover at all, some pairings are seventy-thirty. No single set of stats evens out both. The team decided woods are the balance point, because every generated map has them. And the other surprise: mechanics changes move balance more than stat changes do. When the pushing mechanic went in, it was the biggest balance swing of the week. When woods and ambushes went in, the Choir lost nine to twenty points until it was retuned. So the lesson is that stats compensate for mechanics, and after any combat or AI change, you re-run the table.
MIA: The AI had its own lessons.
SAM: A few. When the team built the six-thousand-soldier benchmark battle, the AI generals just stood and stared at each other. At that size, nobody wanted to commit. So the benchmark uses a scripted charge instead. And later two AIs on opposite sides of a river would wait forever, each refusing to cross. The fix was teaching the AI to find an unwatched ford, or to pull back and bait the enemy across.
MIA: And there was a subtle class of bug in the AI.
SAM: Flags that latch. The team-game AI has states like "I'm waiting for those two to fight" or "I'm pouncing now". Each one switches on when a situation starts, but they also have to switch off when the situation ends, and three of them didn't. Code review caught all three. That's one reason Mario's rule is that every code change gets a simplify pass and a code review before it merges.
MIA: Let's talk about the memory budget, because it changed three times.
SAM: It did, and it's a good lesson in measuring before optimising. The original design target was a hundred and sixty megabytes for the whole game, which sounds heroic. Then the first build measured about a hundred and ninety on Mario's Mac. But when the team broke it down, about a hundred and twenty-one megabytes is Apple's own graphics system, which any app pays just for opening a window. The graphics library added about fifty. Grubcraft's own scene was about fifteen.
MIA: So the target was below the floor before the game even started.
SAM: Right. Chasing it would have cost Mario's time for no visible gain. So he set four gigabytes, and then six, along with six players. The lesson: measure what's actually yours before you set a target. And there's still discipline inside the budget: the battle simulation has tight limits, and an automatic check runs the real game and fails if memory use goes over budget.
MIA: Now some lessons about the project itself. The GitHub minutes story.
SAM: On the thirteenth, every automatic check started failing within two to five seconds, with no logs at all. The code was fine, and the same code had passed minutes earlier. It turned out to be GitHub's included build minutes running out. Mac builds cost ten times the minutes on a private repository, and the game builds on Mac, Windows and Linux for every change.
MIA: And it stayed broken for a while.
SAM: About two days. Mario made the repository public on the fifteenth, which gives free build minutes, and everything started again. The lesson the threads saved: if every job fails instantly with no logs, don't debug the code, it's billing.
MIA: And the status page.
SAM: Mario reads progress on a status page called the Campaign Map in the Claude app. It went stale. Twenty-five merged changes were missing, the headline had turned into a wall of text that every thread appended to, and the Mac download link was out of date. Mario said, fairly, that it wasn't being updated. The fix was to stop relying on threads remembering to hand-edit it. Now a script pulls every merged change, the open work, the build health and the latest download links straight from GitHub, and threads only write one plain sentence per change.
MIA: Same lesson as the map fingerprint.
SAM: Exactly the same lesson. If something has to happen every time, automate it, don't rely on memory.
MIA: Then there was the night Mario was upset.
SAM: Yes. Mario asked for the third wave of review fixes to wait until three in the morning his time. He's in New Zealand. The coordinator set a reminder for itself, but never told the thread doing the work. So the thread just carried on into wave three early. Mario decided to let it keep running, but the lesson is now a rule: when Mario schedules work for later, tell the thread that's doing it immediately. A reminder in one place isn't a message to another.
MIA: There were some small but painful workflow lessons too.
SAM: A few that every thread now knows. GitHub doesn't run any checks on a change that has a merge conflict, so a pull request can sit there looking quiet when it's actually blocked. A green check result doesn't always wake the thread that's waiting for it. One AI change sat green for three hours until the coordinator nudged it. So threads now check for themselves. And one thread accidentally included an unfinished draft file in a commit, so drafts now live in a separate scratch folder, never in the project.
MIA: Let's talk about the art contest, because that was a deliberate experiment.
SAM: It was. Mario wanted to know which setup should build 3D models from now on. So one thread on Opus built the full Ember Clans roster, fifteen models, and a separate thread on Sonnet built the Carrion Concord, fourteen models, with the same rules, the same budgets, and the same engine help. Then a comparison page put them side by side.
MIA: And Mario picked Opus at medium effort.
SAM: Right. And the useful lesson is how to make a choice like that: same brief, same budget, side by side, judged by the person who has to live with the result. There were practical lessons too. Free model kits couldn't reach the fidelity Mario wanted, which is why the models are built from scratch in Blender. And a funny one: if you name a Blender script after a standard Python module, like inspect, Python inside Blender picks up your script instead of the real module, and things break in confusing ways.
MIA: That connects to the cost rule.
SAM: Yes. Mario asked every thread to check where cheaper helper models could do the work at no loss in quality, and to actually use them. Docs updates, adding tests, running benchmarks go to the smallest model. Well-specified features behind the simulation, like menus, rendering and tools, can go to a mid-sized model. But the simulation, the netcode and the replay logic stay with the lead, because those are where one subtle mistake breaks every multiplayer game. And the lead reviews every helper's work and owns the result.
MIA: Last category: working with Mario.
SAM: A few things the team has learned. Mario isn't a programmer, so everything is explained in plain words. Not "lockstep netcode over a UDP link", but "playing over the internet with Tailscale". Docs stay current in the same change as the code, so the design documents never describe features that don't exist. There was a cleanup pass specifically because the architecture docs listed planned features as if they were built.
MIA: And Mario sets the vision firmly.
SAM: Very firmly, and that's helped. Individual soldier duels are vital. Maps must be big and alive. Online battles are the priority. Buildings must show construction stages with the faction's own workers. When those are stated clearly, the threads can make the hundred smaller decisions themselves without stopping to ask.
MIA: If you had to boil the whole series of lessons down?
SAM: Three things. One: if a rule matters, make a machine check it. Whole-number maths, golden replays, memory limits, the status page. Two: measure before you optimise or tune. The memory floor, balance noise, the steep knobs. And three: say things to the right place. Tell the thread, not a reminder. Put the vision in writing, so every session builds toward the same game.
MIA: That's the series. Thanks for listening to The War Table.
SAM: Next time there's a batch of progress, we'll do another round. See you on the battlefield.
