# 11 · Networking

Up to six players on the same Wi-Fi network, any mix of Macs and Windows PCs, one player hosting on their own machine. No servers, no accounts.

*Built (six-player lobbies, 2026-10-16):* the lobby has six slots, the lobby message carries all six, and the protocol is number 8. A test plays six machines in lockstep (`six_machines_play_in_lockstep` in `crates/gc_net/tests/lan_match.rs`).

## Model: host-sequenced deterministic lockstep

Every machine runs the **same deterministic simulation** ([10 · Architecture](10-architecture.md#the-deterministic-simulation)). The only thing sent over the network is **player commands**. Because the simulation is identical everywhere, the same commands in the same order produce the same game on every machine, bit for bit, across Mac ARM and Windows x86 alike.

Why lockstep for an RTS:
- Bandwidth depends on how fast players click, not on how many soldiers exist. Thousands of soldiers cost nothing to synchronise.
- Replays, save games, rejoin and spectating come almost for free.
- It is what classic RTS games used, for the same reasons.

### The twist: the host sequences turns
Classic lockstep makes every player wait for every other player's input each turn, so one player's Wi-Fi hiccup freezes everyone. We avoid that:

1. Each tick is a **turn** (50 ms).
2. Clients send their commands to the host as soon as they're issued.
3. The **host assigns** each command to a future turn, `current turn + D` (the input delay), and broadcasts a **turn bundle** for every turn on a steady 20 Hz cadence, containing all commands from all players for that turn (usually empty).
4. Every machine simulates turn T when it holds bundle T.

The host never waits for clients. A client whose packet arrives late only has *its own* command land a turn later. A client that falls behind (slow CPU, bad Wi-Fi burst) catches up by simulating buffered turns slightly faster; only if a client falls far behind does the host gently slow the turn rate for everyone (time dilation) instead of freezing the game.

The host's own commands go through the same delay, so hosting gives no advantage.

### Input delay
- `D` adapts to measured conditions: `D = ceil((RTT/2 + 2 × jitter + 10 ms) / 50 ms)` for the slowest player, from 1 to 8 turns. As built, jitter is the smoothed mean deviation of the round trip (the way TCP keeps it). Every match starts at 2 turns.
- On wired LAN: 1 turn (50 ms). On typical home Wi-Fi: 2 turns (100 ms). The host looks again every second and moves the delay by one turn at a time. It goes up as soon as it is too short, and down only after three looks in a row found it longer than needed.
- **Local feedback hides the delay:** the moment you click, you hear the unit acknowledge, see the move marker, the formation preview and the selection flash. Units start moving 50 to 100 ms later, which feels instant in an RTS.

## Transport

- Plain **UDP**, one socket per machine, packets kept under 1,200 bytes (safe on any network).
- Our own small reliability layer: every packet carries a sequence number, the latest received sequence and a 32-bit ack bitfield.
- **Redundancy instead of retransmission:** every packet repeats all data the other side hasn't acknowledged yet (the last few turn bundles, or unacknowledged commands). On Wi-Fi, where losses come in bursts, the next packet already contains what was lost, with no retransmit timers and no stalls. Turn bundles are tiny, so this is cheap.
- The host sends a bundle every 50 ms even when empty. This doubles as a keepalive that stops laptop Wi-Fi radios from dozing between packets.
- **Encrypted and authenticated:** X25519 key exchange at join, then ChaCha20-Poly1305 per packet. Cheap enough to always run, so there is one code path whether playing at home or over a virtual LAN. *Built in step 3 (`gc_net::crypt`):* each side makes a fresh key pair per connection and the two swap public keys in the clear (Hi and KeyReply packets). BLAKE3 then derives one key per direction from the shared secret, both public keys and the lobby password (empty when there is none). Every link packet after that is sealed: the 4-byte header stays readable and is authenticated, then come the packet's 8-byte number in that direction (the nonce) and the ciphertext with its 16-byte tag. Without the password nobody can make keys that work, so a joiner who typed it wrong is found at their first packet, and a machine in between can neither read nor change the game.

### Bandwidth
| Direction | Typical | Busy late-game micro |
|---|---|---|
| Client → host | < 0.5 KB/s | ~2 KB/s |
| Host → each client | ~1 KB/s | ~3 KB/s |
| Host total (3 clients) | ~3 KB/s | ~10 KB/s |

Commands are compact binary (a move order for a 12-regiment selection is ~40 bytes: type, regiment ids as delta varints, quantised target, facing, frontage).

**Built so far (M2 step 1, 2026-10-13):** `gc_net` plays Field Battles between up to four machines on one network. Its parts:

- `wire`: varint encoding of commands (a one-regiment move order is 12 to 16 bytes).
- `proto`: packets start with `GC`, a protocol number and a kind: a discovery **query**, a **beacon** answering it, a **link** packet, or a **wrong-protocol** answer that tells a joiner on another protocol which build the host runs (plain and unsigned, so a joiner heeds it only before the host has answered its key). Messages: Hello, Welcome, Refuse, Lobby, Edit, Start, Loaded, Bundle, Orders, Hash, Notice, Bye, and since step 2 Delay, Wait and Desync (protocol 2). Protocol 4 (2026-10-15) carries the formation command and the weapon flags in unit stats; protocol 5 (2026-10-15) carries the lobby's champions option; protocol 6 (step 5a) the points budget and each player's army.
- `link`: the reliability layer as built is simpler than the bitfield described above. Each side numbers its messages; every packet carries "I have all of yours below N" and repeats, oldest first, every message the other side hasn't acknowledged (as many as fit in 1,200 bytes). Lost packets need no timers: the next packet, at most 50 ms later in a match, carries the same messages. Each packet also carries a timestamp and an echo, which gives the round trip and its jitter. A packet counts only once all of it reads: one with a bad message anywhere in it is dropped whole, and its messages come again in the next. Messages are decoded defensively: places, teams and lists out of range are refused rather than read (a lobby may name a map this build lacks, since the version line keeps it from starting, but a match start may not), and tests feed the decoders random and damaged bytes (as they do replay files, which also refuse maps over 4,096 tiles a side and more than 65,536 regiments).
- `Lan` implements the menus' `Network` trait. The host listens on UDP port **47820** (a second game on the same machine takes 47821, up to 47823). Join's list asks every host on the network (a broadcast query each second, plus this machine) and shows those that answer; Join also takes an IP address or `ip:port`, and waits up to 3 seconds for an answer. The host turns a joiner away when the lobby is full, the match has started, or its game data differs from a build with the same rules (it would start and desync at once); a build with other rules is let in and the lobby's version line blocks Start until everyone matches.
- **Match start:** the host sends Start (its seed, a hash of its map's walkable ground, heights, water level and woods and tall grass, the players and each reader's place among them). Each joiner builds the same world from that seed (generating the host's map if its own differs), checks the map hash, and answers Loaded; a joiner whose map came out differently says so and leaves instead of desyncing later. The host raises every army and runs the computer players; their orders reach everyone through the turns like a human's. A joiner may only send orders for its own regiments (move, attack, formation) and Ready: the host drops any other kind of command a joiner sends (spawning, removing or tuning regiments, deployment zones), so a tampered client can't use the sandbox on everyone's game, and it holds at most 640 of a joiner's commands waiting for a turn (16 orders to a whole army) (`Command::is_player_order` in gc_sim, `MAX_QUEUED_ORDERS` in `lan.rs`). The sim itself still accepts sandbox commands from anyone, for local sandbox play and replays. In a network match the host takes the south and a joiner in the north turns its camera to face south.
- **Turns:** the input delay starts at 2 turns (100 ms) and adapts (see Input delay above, built in step 2); the host tells everyone when it changes. When the host simulates turn T it closes every bundle up to turn T + delay and sends them to everyone. When the delay grows, an extra empty bundle closes; when it shrinks, none closes for a turn; a bundle holds at most 900 bytes of commands, and the rest wait for the next turn. Joiners simulate one turn per 50 ms of their own clock while bundles are waiting, catch up a turn at a time when more than the delay plus one are waiting, and wait without stuttering when none are. A host that hitches by more than 20 turns carries on from there rather than rushing everyone.
- **Desync detection:** every 10 ticks each joiner sends its state hash; the host compares it with its own for the same tick and tells everyone "Alex is out of sync with the host (turn N)". Every machine then saves a **desync report**. Since step 6a that is the machine's replay of the match so far (below), a `.gcr` file in a `desync-reports` folder beside `settings.ron`, with the tick the worlds parted at in its header (step 2 had its own `.gcdesync` format, now gone). Played back, a report reproduces that machine's hashes, and `gc_replay compare A B` (`Replay::first_difference`) finds the first tick two machines' reports disagree on (a network match's recording keeps a state hash every 10 ticks, as often as the host compares them, and reuses it for the comparison) and the first tick their orders differ. *Since review fix R12 (2026-10-16):* a report also keeps each system's own hash (`World::system_hashes`: clock, random streams, unit stats, regiments, combat, pathfinding, vision, deployment, verdict, champions) at its last 256 hash ticks (about two minutes, as far back as the host compares; replay format 9), so `compare` names the systems that parted first, such as "regiments, combat". Resyncing a player whose world diverged is not built yet: it needs the sim to save and load its whole state (snapshots), step 6c.
- **Disconnects:** a player silent for 3 seconds (or who quits) is gone from the lobby, and their slot opens. In a match, the lobby's **On drop** setting decides what happens (built in step 2). With **Wait** (the default), the host pauses the match for everyone ("Paused: waiting for Alex to reconnect (85 s)") for up to 90 seconds. If Alex's connection comes back, the match carries on from where it stopped and their machine catches up on the turns it missed. The host can press **P** to carry on without them. With **Play on**, or after 90 seconds, everyone sees "Alex lost connection" and plays on while that army stands and defends. A player who quits says goodbye and is gone at once. A joiner gives up on a silent host after 90 seconds with Wait (5 with Play on, and 5 in the lobby), showing "Lost contact with the host, trying to reconnect" meanwhile. A host that quits ends the match for the joiners. **Rejoining after a restart** is built (step 6b): if Alex's game crashes or closes, they start it again and join the same host (the Join list shows the game as "in progress"). The host gives them back the human place with their name that nobody holds, if they join from the same computer (address) that played it, sends the match's start and every turn so far, and stops waiting for them. Their machine replays the match from the first tick as fast as it can while still drawing (more turns a frame while far behind, `Lan::catching_up`) without a sound or an Ambush alert, since the sounds only note what changed, and everyone sees "Alex rejoined and is catching up". It needs no snapshot, because the turns rebuild the same world; replaying from the start costs a second or two for every minute played in a big battle. Anyone else is still refused ("That game has already started"). The host can give a joined player's place to an AI, which turns them out of the lobby.
- In the game (`gc_game/src/online.rs`), a network match keeps running behind the menu, the sandbox tools (pause, speed, switching sides, placing, removing, tuning) are off, and the battle panel shows the connection (port, input delay, round trips, turns buffered), who the start is waiting for, and any notice. `--host` opens a lobby at launch and `--join ADDRESS` joins one.

Tests (`crates/gc_net/tests/lan_match.rs`) run every machine in one process on an in-memory network (`gc_net::net::MemoryNet`, review fix R14). The `Lan` takes its clock and sockets from a `Net`: `Udp` in the game, the memory network in tests. That network has a clock the test moves a millisecond at a time, and seeded latency, loss, duplication and reordering. Timeouts of seconds pass in a moment, nothing depends on how busy the machine is, and the same seed plays out the same way every run (a test checks this). Joining without blocking is `Lan::start_join` plus `Lan::joining`; the menus' `join` waits on those. One smoke test (`tests/udp.rs`) still finds a host, joins and plays 60 turns over real UDP. Three `Lan`s play 300 turns through 15% loss, 5% doubled packets and 30 to 90 ms latency, and end with identical worlds; a joiner's recording of the match, saved and loaded, plays back to the same world. Other tests cover the delay falling on a fast network and following a slow spell up and back down, garbage and forged packets (from strangers, and spoofed as the other side) changing nothing, a host gone quiet in the lobby, a match pausing for a dropped player and carrying on when they return or when the host stops waiting, Play on, a deliberate desync reported on both machines at the same tick (their recordings show where they parted), refusals, leaving, being replaced, discovery, a host that never answers, and a joiner whose sandbox commands (removing the host's army, retuning a unit, spawning, a deployment zone) are dropped by the host. Two copies of the game were played against each other in the cloud container (software rendering, 6 frames a second) for three minutes with no desync. In step 2, freezing the joiner for 11 seconds paused the host, which resumed when the joiner returned, still with no desync.

**Built in step 2 (2026-10-15):** the adaptive input delay, desync reports, and Wait or Play on when a player drops (all described above).

**Built in step 3 (2026-10-15):** encrypted links, join codes and the lobby password (all described above), protocol 3. `--password WORD` goes with `--host` or `--join`.

*Built in step 4 (2026-10-15):* the battle map is made with whole-number maths only (`gc_map::generate`: fixed-point noise, `gc_fixed`'s sine table and integer square roots), so the same seed gives the identical map on every machine, Mac, Windows or Linux. This replaced the plan to ship baked map files: a seed still makes a fresh map for every match and nothing extra crosses the network. The maps look as before (heights within 0.007 of a tile of the old float version). A test (`the_map_is_the_same_on_every_machine`) pins the fingerprint of maps at 256 and 384 tiles (the size the field golden replay uses) and runs in CI on all three systems; the lobby's map hash check stays as a second guard. Floats are still used to draw the map, and for the computer players' view of it, which only the host runs; those live in `gc_map`'s `view.rs`, and a lint plus the `no_floats` test keep the rest of `gc_map` float-free.

**Built in step 5a (2026-10-15):** the points budget and army builder ([06 · Game modes](06-game-modes.md#field-battle-extras)), protocol 6. The lobby settings carry the budget, each player's slot carries their army (up to 40 regiments, as unit indices; a longer list is refused when read), and a joiner sends theirs with a new Army edit. The host holds every army to the budget and to the player's faction when it raises them, so a tampered army can't field more than the budget. Unit stats carry `points` (unit data schema 6), which is in the data hash every lobby compares.

**Built in step 5b (2026-10-15):** the deployment phase ([06 · Game modes](06-game-modes.md#field-battle-extras)), protocol 7. It is part of the simulation, so it needs nothing new from the network but two commands: the host sends every player's `DeployZone` first, then the armies, then `Ready` for every computer player (a setup too big for one turn spills into the next ones, and zones are accepted until the battle begins), and people's Ready button sends `Ready`. A move order while deploying places the regiment instead of marching it. Every machine sees the battle start on the same tick.

**Built in step 6a (2026-10-15):** replays in the game (see [Save, load and replays](#save-load-and-replays)), and desync reports are replay files. No protocol change.

**Built in step 7 (2026-10-15):** packaging, with no protocol change. One zip per platform, each with a read-me that explains the firewall (Windows) and local network (Mac) prompts LAN play depends on. See [release checklist](release-checklist.md).

**Parked, build only if needed (2026-10-16):** (6c) sim snapshots, and with them resyncing a diverged player and a faster rejoin. Desyncs are detected and reported but not repaired. Build this if out-of-sync notices or desync reports show up in real games. Tracked in [issue #59](https://github.com/mariothapliyal/Grubcraft/issues/59). *Groundwork (review fix R2/T6, 2026-10-16):* the regiment pool now lists its per-regiment fields once (`regiment_fields!` in `gc_sim/src/regiments.rs`), and that one list makes the pool, resets a slot, copies one into a forked world, hashes it and writes and reads it for a snapshot (`gc_sim/src/state.rs`), so a new field can't be left out of any of them; tests check every field reaches the state hash and that a pool reads back exactly and plays on alike. The other systems (combat, pathfinding, vision) get the same treatment before 6c is built. Hashing every field (the old hash skipped some while they held their starting value) moved the sim to version 5. M2's netcode is otherwise complete, and plays over the internet with Tailscale (see [Playing beyond one Wi-Fi network](#playing-beyond-one-wi-fi-network)).

## Session flow

```
Host                         Client
 │  beacon (LAN broadcast + mDNS, every 1 s)
 │──────────────────────────────▶ appears in Join list
 │◀──── Hello (build hash, data hash, name, key share)
 │───── Welcome (slot, lobby state, key share) ───────▶
 │  lobby updates (faction, team, colour, ready) ⇄
 │───── Start (seed, settings, start turn) ───────────▶
 │◀──── Loaded ──────────────────────────────────────── (barrier)
 │───── Countdown 3·2·1, turn bundles begin ──────────▶
```

- **Discovery:** UDP broadcast beacon plus mDNS service `_grubcraft._udp`. Friends on the same network see the game without typing anything.
- **Direct join:** IP and port, or a short **join code** that encodes them (for virtual LANs and port-forwarding). *Built in step 3 (`gc_net::joincode`):* the code is eight characters of Crockford base 32, like `K7QD-M2XA`. It holds the host's IPv4 address, which of the four game ports it is on, and six check bits that catch most typos. Case and dashes don't matter, and O, I and L read as 0, 1 and 1. The host's lobby shows its code and address. When Tailscale is running it also shows a **Tailscale code** for the host's Tailscale address (100.64.0.0/10, found by asking which address would reach Tailscale's own 100.100.100.100), so friends anywhere can join with a code (`joincode::tailscale_ip`).
- **Version gate:** the Hello carries the build hash and the game-data hash. Mismatches are rejected with a clear message naming both versions. *Built (review fix R3, 2026-10-16):* a build's name is "VERSION sim N (COMMIT)", where N is `gc_sim::SIM_VERSION`, the simulation's rules version, bumped whenever the golden replays need blessing. The lobby blocks Start unless everyone's version and sim version match; the commit is shown but not compared, so builds that differ only in docs or art play together.
- Optional lobby password. *Built in step 3:* the host types it on the Play screen, and it goes into the link keys rather than across the network. The Join list marks locked games "(password)". A joiner is told "That game needs a password", "Wrong password" or "That game has no password". One address gets five wrong-password answers a minute; past that the host ignores it altogether (no key exchange either, so it can't keep guessing silently) until the minute is up, unless it holds a place in the match (a player rejoining). The joiner then sees "No answer". Games without a password count no guesses.

## Desync detection and recovery

Determinism is engineered and tested ([10 · Architecture](10-architecture.md#testing-strategy)), but we plan for failure:

1. Every 10 turns each client sends the host a 64-bit hash of its simulation state.
2. On a mismatch, the host takes the majority hash as truth (the host's own state breaks ties).
3. Divergent clients receive a **snapshot** (300 KB to 1 MB, compressed) plus the commands since, load it, and continue. Players see a brief "Resyncing…" banner rather than a lost game.
4. Everyone writes a **desync report**: the last snapshot before divergence plus the input log. `gc_replay` can rerun that on both platforms and, in debug builds, compare per-system hashes tick by tick to find exactly which system diverged.

## Disconnects and rejoining

- A client silent for 3 s is marked disconnected. Lobby option: **Pause and wait** (default, up to 90 s) or **Continue**.
- A disconnected player's units do nothing new but still defend themselves by simulation rules. In team games, an ally can take control; a later lobby option lets an AI run their army until they return ([18 · AI](18-ai.md#ai-allies)).
- **Rejoin:** the player relaunches and joins the same host. Built in step 6b without snapshots: the host sends every turn from the start and the client replays them all. Later the host sends the latest snapshot and the commands since; the client fast-forwards. A tick costs 1 to 2 ms, so catching up on a minute of play takes about 2 to 3 seconds.
- **Host leaves:** at launch the game ends (with an automatic save so it can be resumed). **Host migration** is planned: since every client holds the full state, the client with the best connection becomes the new sequencer from the last turn everyone had, and the others reconnect to it. AI players move with it: their minds keep nothing that can't be rebuilt from the sim, so the new host restarts them and they re-scout.

## Save, load and replays

- **Multiplayer save:** the host saves a snapshot plus metadata. Loading it in a lobby lets players reclaim their slots and continue.
- **Replays** are the match header (build, data hash, settings, seed, players) plus the turn-by-turn command stream, delta-encoded and LZ4-compressed: about **50 to 150 KB per hour** of play. Every match is saved automatically.
- Seeking in long replays uses keyframe snapshots the viewer generates on first playback and caches locally.
- Replays are tied to the build and data hash they were recorded with. For a personal game that's acceptable; the replay browser marks incompatible ones.

**Built so far (M1 exit, 2026-10-15):** the replay file and its tools, `gc_replay`, used for the golden replays. A `.gcr` file is the magic `GCRP`, a format number, then an LZ4-compressed body: a note, the seed, the regiment capacity, the unit table, teams, the walkable-ground costs, the heights and (since format 3) the woods and tall grass of [20 · Ambushes](20-ambushes.md), so the map needs no generator; then the command of every tick that had any, and the state hash at tick 0 and every second after. It has its own command encoding, separate from `gc_net::wire`, so a protocol change never invalidates stored replays; a change to the simulation's commands or unit stats does, and bumps the format (format 2, 2026-10-15, added formations and the weapon flags, and the goldens were recorded again; format 3 added the cover layer, and format 2 files still load, as maps without cover; format 4 stores whether the match allows champions, and older files load as matches without them; format 5 adds the deployment commands; format 6 adds a header, below, and older files load with an empty one; *since 2026-10-16* format 10 writes the header, note, seed, map size, unit count, teams and ticks as a small block of its own before the compressed rest, so the Replays screen's list reads just that block (`Replay::read_header`) instead of decompressing up to 50 whole files; older files still load and are read whole for the list; saving a replay is atomic, as the game's own saves). `gc_replay::Recorder` records any match (`Recorder::new(&setup, &world, note)`, then `recorder.tick(&mut world, &commands)` in place of `world.tick`). Most of a short replay is the stored map (about 90 KB for a 256-tile map); the commands of a 4-minute 2v2 take about 10 KB.

**Built in M2 step 6a (2026-10-15):** every Field Battle is recorded, on one machine or over the network, and every machine in a network match records its own copy. The file goes in a `replays` folder beside `settings.ron`, named by the date and time it started (UTC) and the mode. It is saved once a minute of game time, when the battle is decided, when you open the Replays screen, and when you leave the battle or quit, so a crash loses at most a minute; the newest 50 are kept. Format 6's header names the build, the game data's hash, the players (name, colour, faction) and whose machine recorded it, and for a desync report the tick the worlds parted. **Replays** on the main menu lists them, newest first, a page at a time ("Red (Mario) v Violet (AI 2)", when and how long), and **Watch** plays one: the map is made from the stored seed (if this build makes a different map from it, a line says so and the soldiers still walk the stored one), every regiment is in view (`V` shows only what the followed side saw), `Tab` follows another side, `P` pauses, `-` and `=` change the speed, the deployment phase plays 8 times faster, and the panel shows the time and when the replay is over. Ordering, placing, tuning and the other sandbox tools are off. A replay recorded with a unit table of another size can't be shown (its unit numbers would name other regiments) and the list says so; one with other game data of the same size plays, marked "older game data". `gc_replay info` prints the header and `gc_replay compare A B` compares two machines' recordings. Not built yet: keyframes for seeking, a timeline, and the post-game screen's Watch button.

## Playing beyond one Wi-Fi network

In order of effort:

1. **Now:** a virtual LAN tool such as Tailscale or ZeroTier. Friends install it once, the host shares their computer with them in Tailscale, and they join with the lobby's Tailscale code or the host's 100.x address. The Join list only finds games on the same Wi-Fi. No code needed from us, and traffic is end-to-end encrypted by the tool as well as by us.
2. **Later:** port forwarding on the host's router, with a connection-test button in the Host screen.
3. **Later still:** UDP hole punching through a tiny rendezvous service so join codes work across the internet without extra software.

## Known trade-offs

- **Map hacking is possible** in lockstep, because every machine holds the full state. Among friends this is acceptable; we do not build anti-cheat.
- **Everyone runs the full simulation**, so the slowest machine sets the ceiling. That is why the simulation budget is tiny ([12 · Performance](12-performance.md)).
- **AI players run on the host only.** Each is a player whose commands the host puts in the turn bundles, tagged with the AI's slot like anyone's, so they cost the other machines nothing and replays record them like human orders ([18 · AI](18-ai.md#the-big-decision-rules-in-the-simulation-minds-outside-it)). The host pays for their thinking, on its own thread.
- **One build for everyone:** players must update together. The version gate makes this obvious rather than mysterious.
